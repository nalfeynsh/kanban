# API v1: интеграция с внешними системами

Документ описывает протокол обмена задачами между «Моим Канбаном» и внешней системой
(в частности, доской Игоря). Наша сторона уже реализует этот контракт; принимающая
сторона должна реализовать те же методы или адаптер к ним.

Практическое задание для Игоря, чек-лист приёмки и список передаваемых документов:
[igor-integration-handoff.md](./igor-integration-handoff.md).

## 1. Базовый адрес и авторизация

```
Base URL: https://kanban.layero.app/api/v1
Auth:     Authorization: Bearer kb_...
          (альтернатива: X-API-Key: kb_...)
```

Токен создаёт администратор в интерфейсе: **Команда → Интеграции → Создать токен**.
Показывается он один раз; в базе хранится только SHA-256. Отзыв токена мгновенно
прекращает доступ.

Все ответы — JSON. Ошибки:

```json
{ "error": "invalid_token", "message": "..." }
```

Коды: `401` — нет/неверный токен, `403` — нет права, `404` — объект не найден,
`400` — неверные данные, `500` — внутренняя ошибка.

## 2. Модель задачи

| Поле | Тип | Примечание |
|---|---|---|
| `id` | uuid | внутренний id; в ответах нашего API |
| `title` | string | обязательное при создании |
| `description` | string | HTML или текст, как есть |
| `column_id` | uuid | id колонки нашего API |
| `column_title` | string | альтернатива `column_id` для внешней системы |
| `due_at` | ISO-8601 / null | срок |
| `start_at` | ISO-8601 / null | начало |
| `priority` | 0,1,2 | 0 — обычный, 1 — средний, 2 — высокий |
| `deleted_at` | ISO-8601 / null | `null` — активна, дата — в архиве |
| `updated_at` | ISO-8601 | версия записи для разрешения конфликтов |
| `external_source` | string | `kanban` или `igor` — кто создал |
| `external_id` | string | стабильный id во внешней системе |

`external_id` — **ключ идемпотентности**. Он уникален: повторная отправка того же
`external_id` обновляет задачу, а не создаёт новую.

## 3. Методы

### `GET /columns`

```json
{ "data": [ { "id": "…", "title": "Сделать", "position": 1 } ] }
```

### `GET /tasks?since=<ISO>&limit=200`

Возвращает задачи, изменённые **после** `since`, включая архивные (tombstones: у них
заполнен `deleted_at`). Это курсор для polling.

```json
{
  "data": [
    {
      "id": "…",
      "title": "Проверить договор",
      "description": "…",
      "column_id": "…",
      "due_at": null,
      "priority": 1,
      "updated_at": "2026-11-14T09:00:00Z",
      "deleted_at": null,
      "external_source": "kanban",
      "external_id": "…"
    }
  ]
}
```

### `GET /tasks/:id`

Одна задача по внутреннему `id`.

### `POST /tasks` — создать или обновить

```json
{
  "external_id": "igor-123",
  "external_source": "igor",
  "title": "Задача из доски Игоря",
  "description": "<p>Описание</p>",
  "column_title": "Готово",
  "due_at": "2026-11-20T18:00:00Z",
  "priority": 1,
  "updated_at": "2026-11-14T09:00:00Z"
}
```

Ответ:

```json
{ "data": { "id": "…", "…": "…" }, "created": true, "skipped": false }
```

Правила:

- поиск идёт по `external_id`; если не найден, но передан `id` существующей локальной
  задачи — обновляется она (первая публикация без дубля);
- если локальная `updated_at` **новее** переданной, изменения не применяются:
  `skipped: true`, в `data` возвращается локальная версия. Синхронизатор должен
  затем отправить локальную версию обратно;
- `deleted_at` в теле переносит задачу в архив; отсутствие поля не отменяет архив;
- `column_title` ищется без учёта регистра; если не найдено — первая колонка.

### `POST /tasks/archive` — архивировать по внешнему id

```json
{ "external_id": "igor-123", "source": "igor" }
```

## 4. Двусторонняя синхронизация

Рекомендуемый цикл (polling, без вебхуков):

1. **Pull от Игоря:** `GET {IGOR}/tasks?since={lastPull}`.
2. Для каждой задачи вызвать наш `POST /tasks` с `external_id` и `updated_at`.
   `skipped: true` означает, что локальная версия новее — её нужно отправить обратно.
3. **Push к Игорю:** `GET {OURS}/tasks?since={lastPush}`; для каждой задачи вызвать
   `POST {IGOR}/tasks` с `external_id` (для локальной задачи — её `id`) и `updated_at`.
4. Сохранить `lastPull`/`lastPush` (время последнего успешного прохода).
5. Повторять раз в 1–5 минут; при ошибке — с тем же курсором.

Правило конфликтов: **побеждает запись с более поздним `updated_at`**.
`updated_at` должен быть в UTC ISO-8601. Если время одинаковое — запись считается
уже синхронизированной.

Удаление: не удаляйте строки физически; ставьте `deleted_at`. Обе стороны передают
архивные записи в `GET /tasks`, чтобы удаление доехало.

## 5. Что нужно от доски Игоря

Минимальный контракт принимающей стороны:

```
GET  {IGOR}/tasks?since=<ISO>&limit=200
POST {IGOR}/tasks
POST {IGOR}/tasks/archive
```

- `POST /tasks` принимает те же поля, ищет по `external_id`, уважает `updated_at`.
- Ответы — `{ "data": ... }`.
- Если у Игоря уже есть свой API, достаточно адаптера: сопоставить его поля с таблицей
  из раздела 2 и реализовать upsert по `external_id`.
- Нужны базовый URL, токен и подтверждение полей/статусов колонок.

## 6. Готовый синхронизатор

В репозитории: `tools/igor-sync.mjs`.

```bash
KANBAN_API_URL=https://kanban.layero.app/api/v1 \
KANBAN_API_TOKEN=kb_... \
IGOR_API_URL=https://igor.example/api/v1 \
IGOR_API_TOKEN=... \
node tools/igor-sync.mjs
```

Скрипт хранит курсоры в `.igor-sync-state.json` (можно указать `SYNC_STATE_FILE`).
Его можно запускать по cron или вручную. Пока API Игоря не готов, скрипт можно
проверить на любом совместимом mock-сервере.

## 7. Безопасность

- Токены передавайте только по HTTPS и только Игорю; не коммитьте в репозиторий.
- Для интеграции создайте отдельный токен с именем «Доска Игоря» и отзывайте при
  компрометации.
- API отдаёт только **командные** задачи: `is_private = true` не возвращается,
  не обновляется и не архивируется через API (ответ `404`).
- API не отдаёт пароли, профили и личные контакты — только задачи и колонки.
