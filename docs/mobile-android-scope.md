# Мобильное приложение «Мой Канбан» — Android first

Дата: 2026-11-17
Статус: решения приняты, следующий шаг — прототип доски и задачи

## 1. Короткий вывод

Для текущего продукта оптимален не переписывание с нуля, а **обёртка существующего
React-приложения под Android через Capacitor** с отдельной мобильной адаптацией интерфейса.

- Весь функционал уже работает в веб-версии: задачи, проекты, этапы, календарь, Гант,
  встречи, чат, файлы, уведомления, аналитика, архив, роли.
- Capacitor позволяет сохранить один код и добавить нативные возможности: push,
  камеру/файлы, deep links, хранение токенов, системный «Поделиться».
- Обновления интерфейса и бизнес-логики можно выпускать чаще, чем обновления
  приложения в Google Play.

Полное переписывание на React Native/Flutter для первой Android-версии не
рекомендуется: это в 2–3 раза больше работы и высокий риск потерять уже готовые
календарные, DnD- и файловые сценарии.

### Принятые решения

1. **Технология: Capacitor + текущий React.** Не React Native и не Flutter.
2. **Push: да, в MVP.** FCM + нативные локальные напоминания; Supabase Realtime
   не считать надёжным каналом в фоне.
3. **Встречи: без встроенного ВКС и без VK.** В MVP — встреча с участниками,
   датой/временем и **полем для ссылки на сторонний сервис** (SberJazz, Телемост,
   VK Звонок и т.п.). Подключение открывает ссылку в браузере/Custom Tabs.
4. **Первый прототип: только мобильная доска и карточка задачи.** Остальной
   проект не трогаем.

## 3. Варианты реализации

| Вариант | Срок MVP | Стоимость поддержки | Плюсы | Минусы |
|---|---|---|---|---|
| **Capacitor + текущий React** | 12–20 недель | Низкая | Один код, почти все сервисы сразу, нативные push/файлы/deep links | Нужна мобильная адаптация UI, WebView-ограничения |
| **PWA / TWA** | 6–10 недель | Минимальная | Быстро, обновления мгновенно, без нативных модулей | Слабые push/файлы/фон, ограниченный store-опыт |
| **React Native / Expo** | 26–40 недель | Высокая | Нативный UI, хороший store-опыт | Переписывание всех экранов, WebRTC/календарь/DnD заново |
| **Flutter** | 30–45 недель | Высокая | Единый нативный UI | Полный rewrite, отдельная команда |

Рекомендация: **Capacitor + responsive web** как основной путь. При жёстком сроке
«только посмотреть, как это на телефоне» — сначала PWA/TWA, затем тот же код
упаковать в Capacitor.

### Сравнение по критериям заказчика

| Критерий | Capacitor | React Native | Flutter | PWA/TWA |
|---|---|---|---|---|
| **Стабильность** | Высокая: один web-код, предсказуемый WebView | Средняя: больше native-мостов и платформенных различий | Средняя: отдельный runtime и плагины | Высокая, но ограничена браузером |
| **Быстродействие** | Достаточное для доски, чата, календаря; тяжёлые анимации — слабее native | Высокое, близко к native | Высокое | Среднее, зависит от браузера |
| **Масштабирование** | Один код и один backend; новые экраны — в React | Нужны отдельные mobile-экраны и интеграции | Нужен отдельный код и команда | Один код, но ограниченный native-функционал |
| **Покрытие функционала** | Почти всё текущее работает сразу | Всё придётся переносить заново | Всё придётся переносить заново | Почти всё, кроме нормального push/файлов |
| **Push** | Да, FCM | Да | Да | Ограниченно |
| **Обновления** | Web-часть — быстро; native shell — реже | Только через store/OTA-сервис | Только через store | Мгновенно |
| **Срок MVP** | 12–18 недель | 26–40 недель | 30–45 недель | 6–10 недель |

Итог: **Capacitor** — лучший баланс для текущего продукта. React Native/Flutter
имеют смысл только при полном отказе от web-кода и большом бюджете на переписывание.


## 4. Рекомендуемая архитектура

```
Supabase (Auth/Postgres/Storage/Realtime)
        │
React + Vite (existing web app)
        │
Capacitor Android shell
  ├── native push (FCM)
  ├── camera/files/share
  ├── deep links: /meet, /g, /vk-auth, reset-password
  ├── secure storage for session
  └── app update/version gate
```

### Что остаётся общим

- UI и бизнес-логика — один React-код.
- Supabase JS client.
- Feature flags и тарифы.
- Календарь, задачи, проекты, чат.
- Веб-версия и Android используют один backend.

### Что добавляется нативно

- FCM push и локальные напоминания.
- Разрешения камеры/микрофона/уведомлений.
- Системный выбор файлов, камера, скачивание/шаринг.
- Deep links и обработка `intent://`.
- Безопасное хранение refresh token.
- Проверка минимальной версии оболочки.

## 5. Мобильный интерфейс

Нельзя просто уменьшить десктоп. Нужен отдельный мобильный слой:

### Навигация

- Нижняя панель: **Доска · Календарь · Чат · Команда · Ещё**.
- «Ещё» — проекты, архив, аналитика, помощь, настройки.
- Гант на телефоне — read-only или отдельный упрощённый режим.

### Доска

- Одна колонка на экран с горизонтальным свайпом между колонками.
- Long-press для drag, крупные зоны захвата.
- Карточка: название, срок, исполнитель, приоритет; детали — в full-screen sheet.

### Задачи

- Full-screen модалка вместо окна по центру.
- Sticky-кнопка «Сохранить», клавиатура не перекрывает поля.
- Файлы: камера/галерея/документы.
- TipTap: упрощённая панель форматирования.

### Календарь

- По умолчанию «День» или «Повестка», месяц — вторично.
- Создание по тапу на слот.
- Перенос встреч — long-press.

### Чат

- Список диалогов → чат.
- Учёт клавиатуры, автоскролл, вложения.
- Push при закрытом приложении.

### Встречи

- В MVP — не видеопровайдер, а **встреча с участниками, датой/временем и ссылкой**
  на SberJazz/Телемост/VK Звонок.
- Поле «Ссылка на встречу» — как в Google Calendar.
- «Подключиться» открывает ссылку в браузере или Chrome Custom Tabs.
- Разрешения камеры/микрофона нужны только если внешний сервис сам их запросит.
- VK ID, встроенный Jitsi/LiveKit и запись в MVP не входят.

### Общие правила

- Минимальная зона нажатия 44×44 px.
- Bottom sheets вместо маленьких поповеров.
- Тёмная/светлая тема.
- Никаких горизонтальных таблиц без адаптации.
- Состояния загрузки/ошибок/пустые состояния.

## 7. Обновления

### Веб-часть

- Деплой на Layero обновляет веб-версию.
- В Capacitor можно либо бандлить web-сборку в APK/AAB, либо использовать
  remote URL/OTA-обновления.
- Для Google Play безопаснее **бандлить web-ассеты** и обновлять их через
  контролируемый OTA-механизм, а не загружать произвольный код.

### Нативная оболочка

- Версия оболочки и минимальная поддерживаемая версия проверяются через
  `/api/app/version` или Supabase.
- Критические изменения API → обязательное обновление.
- Обычные фичи → feature flags и мягкий rollout.
- Каналы: internal → closed testing → production.

### Рекомендуемая схема

- Web UI/логика: релизы раз в 1–2 недели.
- Android shell: 1 раз в 1–2 месяца или при новых native-разрешениях.
- Feature flags позволяют включать модули без нового APK.

## 8. Сложность и оценка

Оценка для одного сильного full-stack разработчика, без дизайнера:

| Этап | Оценка |
|---|---|
| Аудит, мобильный UX, дизайн-система | 2–3 недели |
| Мобильная адаптация основных экранов (доска, задачи, проекты) | 3–4 недели |
| Календарь, чат, команда, архив | 2–3 недели |
| Android-оболочка Capacitor, deep links, push, файлы | 2–3 недели |
| Встречи: участники + внешняя ссылка | 0,5–1 неделя |
| QA на устройствах, Play Console, релиз | 2–3 недели |
| **Итого MVP** | **12–18 недель** |

С дизайнером и вторым разработчиком можно сократить до **8–12 недель**.
Полный паритет со всеми модулями и полировкой — **4–6 месяцев**.

React Native-переписывание: ориентировочно **6–10 месяцев** и выше риск
регрессий в календаре/WebRTC/DnD.

## 9. Риски

1. **Push** — FCM требует настройки проекта и серверной отправки.
2. **Фоновые уведомления** — Supabase Realtime не работает надёжно в фоне;
   нужен FCM.
3. **Файлы** — Android SAF и права доступа.
4. **Google Play** — политика обновлений и WebView.
5. **DnD на touch** — нужен отдельный UX, иначе будет «дёргаться».
6. **Внешние встречи** — ссылка может быть недоступна из рабочей сети; приложение
   не может это исправить, только открыть её в браузере.
7. **Размер WebView** — тяжёлый бандл, нужно ленивое подключение модулей.
8. **Безопасность** — токены в Keystore, проверка deep links.

## 10. План внедрения

### Этап 0. Решение и аудит — 1–2 недели

- Capacitor утверждён.
- Список экранов и приоритетов.
- **Прототип только доски и карточки задачи** — без изменения остального проекта.
- Проверка на реальном Android-устройстве.

### Этап 1. Мобильный веб — 4–6 недель

- Нижняя навигация.
- Доска с горизонтальными колонками.
- Full-screen задача.
- Календарь «День/Повестка».
- Чат и файлы.
- Адаптив команды/аналитики.

### Этап 2. Android-оболочка — 2–3 недели

- Capacitor, подпись, AAB.
- Deep links, auth, secure storage.
- **FCM push в MVP.**
- Камера/файлы/шаринг.
- Экран «Обновить приложение».

### Этап 3. Встречи — 0,5–1 неделя

- Участники, дата/время.
- Поле «Ссылка на внешнюю встречу».
- Открытие ссылки в браузере/Custom Tabs.
- Без VK ID, Jitsi, LiveKit и записи.

### Этап 4. QA и релиз — 2–3 недели

- Internal testing → closed → production.
- Crashlytics/логи.
- Метрики запуска и ошибок.
- План обновлений.

### Первый прототип — отдельная задача №111

Прототип уже доступен: <https://kanban.layero.app/mobile-prototype>.

В прототип входят только:

- мобильная доска: одна колонка на экран, свайп между колонками;
- карточка задачи: full-screen, название, срок, исполнитель, приоритет,
  описание и базовые действия;
- нижняя навигация-заглушка;
- проверка на реальном Android-устройстве.

Не входят: чат, календарь, встречи, команда, аналитика, Capacitor-сборка.
Остальной проект не меняется.

## 11. Что уже решено и что осталось

Решено:

1. **Capacitor** — основная технология.
2. **Push** — нужен в MVP, через FCM.
3. **Встречи** — участники + внешняя ссылка, без ВКС.
4. **Первый прототип** — только доска и задача.

Осталось решить:

1. Нужен ли офлайн-режим в MVP.
2. Минимальная версия Android (рекомендую 8+).
3. Дизайнер/разработчик и срок.
4. Кто публикует в Google Play.
5. Нужен ли push только для чата или ещё для напоминаний задач.

## 12. Рекомендация

Начать с **Capacitor + мобильной адаптации ключевых экранов**, а не с полного
переписывания. Первый Android MVP: доска, задачи, проекты, календарь, чат,
уведомления, команда, архив. Гант и аналитику — во вторую очередь.
Встречи — как в Google Calendar: участники + ссылка на внешний сервис.

Это даёт максимальное покрытие уже работающих сервисов при минимальном риске
и позволяет выпускать обновления без переиздания приложения на каждое изменение.
