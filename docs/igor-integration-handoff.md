# Передача интеграции с доской Игоря

Дата: 14.11.2026. Статус: **наша сторона готова, сторона Игоря — нет**.

Документ — отдельное задание для передачи Игорю. Он описывает, что нужно сделать
на его стороне, какие документы и доступы передать, как проверить интеграцию и что
считается готовностью.

Связанный контракт: [integration-api.md](./integration-api.md).

---

## 0. Сначала — обязательная проверка на нашей стороне

Перед выдачей токена Игорю нужно закрыть один security-пункт.

В текущей реализации `api_v1_tasks` / `api_v1_task` выбирают задачи без фильтра
`is_private` (см. `supabase/migrations/012_api_integrations.sql`). Это значит, что
API-токен может отдать **личные задачи**, хотя интеграция задумана для командных.

**Действие до передачи токена:**

- [ ] Закрыть в API доступ к `is_private = true` или добавить отдельный scope
  `tasks:private` и по умолчанию его не выдавать.
- [ ] Проверить, что `GET /api/v1/tasks` не возвращает личные задачи, а
  `GET /api/v1/tasks/:id` для личной задачи отдаёт `404`.
- [ ] Проверить, что `POST /api/v1/tasks` не может обновить чужую личную задачу
  по `id`.
- [ ] Только после этого создавать токен «Доска Игоря».

Пока этот пункт не закрыт, токен Игорю **не передавать**.

## 2. Что должен сделать Игорь

### 2.1. Поднять API на своей стороне

Минимальный набор методов:

| Метод | Назначение |
|---|---|
| `GET /tasks?since=<ISO>&limit=200` | Отдать задачи, изменённые после `since`, включая архивные |
| `POST /tasks` | Создать или обновить задачу по `external_id` |
| `POST /tasks/archive` | Пометить задачу архивной по `external_id` |
| `GET /columns` | Опционально: отдать свои колонки для сопоставления |

Если у Игоря уже есть API, можно не копировать контракт дословно, а сделать
**адаптер** к этим четырём операциям.

Формат ответов:

```json
{ "data": ... }
```

Ошибки:

```json
{ "error": "invalid_token", "message": "..." }
```

Коды: `400` — неверные данные, `401` — нет/неверный токен, `403` — нет права,
`404` — не найдено, `409` — конфликт (если используется), `429` — rate limit,
`500` — внутренняя ошибка.

### 2.2. Настроить авторизацию

- только HTTPS;
- принимать `Authorization: Bearer <token>`;
- по желанию — альтернативу `X-API-Key`;
- хранить только хеш токена;
- дать возможность отозвать токен;
- не отдавать токен в логах и ошибках;
- CORS не нужен: обмен идёт server-to-server.

### 2.3. Реализовать upsert по `external_id`

Правила:

1. Искать задачу по `external_id`.
2. Если не найдена — создать.
3. Если найдена — сравнить `updated_at`:
   - remote `updated_at` новее — обновить;
   - локальный `updated_at` новее — не перетирать, вернуть `skipped: true`
     и текущую версию.
4. `deleted_at` — это архивирование, не физическое удаление.
5. Не удалять строки физически: обе стороны должны отдавать tombstones в
   `GET /tasks`, иначе удаление не доедет.
6. `external_id` обязан быть стабильным и уникальным. Не использовать
   auto-increment, который может переиспользоваться.

### 2.4. Настроить поля

| Поле API | Обязательность | Что делать Игорю |
|---|---|---|
| `external_id` | да | Стабильный ID задачи в его системе |
| `title` | да | Название; пустое не отправлять |
| `description` | нет | HTML или текст, как есть |
| `column_id` | нет | Предпочтительно, если колонки синхронизированы |
| `column_title` | нет | Альтернатива: название колонки, регистр не важен |
| `due_at` | нет | ISO-8601 UTC или `null` |
| `start_at` | нет | ISO-8601 UTC или `null` |
| `priority` | нет | `0` — обычный, `1` — средний, `2` — высокий |
| `deleted_at` | нет | `null` — активна, дата — архив |
| `updated_at` | да | UTC ISO-8601; без него конфликты не разрешить |
| `external_source` | да для нас | `igor` для его задач, `kanban` для наших |

Если у Игоря другая модель приоритетов — нужна явная таблица маппинга, например:

| Его приоритет | Наш `priority` |
|---|---|
| Низкий | 0 |
| Средний | 1 |
| Высокий / критический | 2 |

Если у Игоря другая модель колонок — нужна таблица:

| Его статус/колонка | Наша колонка |
|---|---|
| To do | Сделать |
| In progress | В работе |
| Done | Готово |

Если колонка не найдена по названию, наш API кладёт задачу в первую колонку —
это лучше явно проверить в тестах.

### 2.5. Настроить пагинацию и курсор

- `since` — строгое «после» (`updated_at > since`), не «включительно».
- `limit` — до 500; `GET /tasks` возвращает до 500.
- Если пришло 500 записей, синхронизатор должен продолжить со следующего
  `updated_at`, а не считать, что данных больше нет.
- Одинаковый `updated_at` у нескольких задач не должен приводить к зацикливанию:
  используйте tie-breaker по `id` или увеличивайте курсор на миллисекунду.

### 2.6. Настроить надёжность

- таймаут запроса: 10–15 секунд;
- retry на `429`/`5xx`: 3 попытки с backoff;
- не retry на `400`/`401`/`403`/`404`;
- идемпотентность: повторный `POST /tasks` с тем же `external_id` не создаёт дубль;
- логировать `external_id`, статус, длительность; не логировать тело с персональными
  данными и токены;
- синхронизация не должна запускаться в два процесса одновременно — нужен lock
  или один scheduler.

### 2.7. Подготовить тестовый контур

- [ ] staging URL;
- [ ] отдельная тестовая задача;
- [ ] тестовый токен;
- [ ] возможность очистить тестовые данные после приёмки.

## 3. Как работает синхронизация

Рекомендуемый цикл — polling, без вебхуков (проще и надёжнее для MVP):

1. Забрать изменения у Игоря:
   `GET {IGOR}/tasks?since={lastPull}`.
2. Применить их у нас через `POST {OURS}/tasks`.
3. Забрать изменения у нас:
   `GET {OURS}/tasks?since={lastPush}`.
4. Отправить их Игорю через `POST {IGOR}/tasks`.
5. Сохранить `lastPull` и `lastPush`.
6. Повторять каждые 1–5 минут; при ошибке — с тем же курсором.

Правило конфликта: **побеждает более поздний `updated_at`**.
Если время одинаковое — запись считается уже синхронизированной.

Готовый синхронизатор: `tools/igor-sync.mjs`.

Переменные:

```bash
KANBAN_API_URL=https://kanban.layero.app/api/v1
KANBAN_API_TOKEN=kb_...
IGOR_API_URL=https://...
IGOR_API_TOKEN=...
SYNC_STATE_FILE=.igor-sync-state.json
node tools/igor-sync.mjs
```

Требования к запуску:

- один процесс на расписание;
- постоянный диск для `.igor-sync-state.json`;
- логи и алерт при ошибке;
- секреты — только в env/секрет-хранилище.

## 4. Примеры запросов

### 4.1. Проверка API

```bash
curl -s https://kanban.layero.app/api/v1/health
```

### 4.2. Колонки

```bash
curl -s https://kanban.layero.app/api/v1/columns \
  -H "Authorization: Bearer kb_..."
```

### 4.3. Получить изменения

```bash
curl -s "https://kanban.layero.app/api/v1/tasks?since=2026-11-14T00:00:00Z&limit=200" \
  -H "Authorization: Bearer kb_..."
```

### 4.4. Создать/обновить задачу

```bash
curl -s -X POST https://kanban.layero.app/api/v1/tasks \
  -H "Authorization: Bearer kb_..." \
  -H "Content-Type: application/json" \
  -d '{
    "external_id": "igor-123",
    "external_source": "igor",
    "title": "Задача из доски Игоря",
    "description": "<p>Описание</p>",
    "column_title": "В работе",
    "priority": 1,
    "due_at": "2026-11-20T18:00:00Z",
    "updated_at": "2026-11-14T09:00:00Z"
  }'
```

Ответ:

```json
{
  "data": { "id": "…", "title": "…" },
  "created": true,
  "skipped": false
}
```

Если вернулось `skipped: true`, значит у нас версия новее. Синхронизатор должен
отправить её обратно Игорю и не затирать.

### 4.5. Архивировать

```bash
curl -s -X POST https://kanban.layero.app/api/v1/tasks/archive \
  -H "Authorization: Bearer kb_..." \
  -H "Content-Type: application/json" \
  -d '{"external_id":"igor-123","source":"igor"}'
```

## 5. Приёмка

Игорь должен подтвердить прохождение тестов на staging:

| № | Тест | Ожидание |
|---|---|---|
| 1 | `GET /health` | `200`, `{ ok: true }` |
| 2 | Запрос без токена | `401` |
| 3 | `GET /columns` | Список колонок, которые можно сопоставить |
| 4 | Создать задачу с новым `external_id` | Создана один раз |
| 5 | Повторить тот же `POST` | Дубля нет, `skipped`/идемпотентно |
| 6 | Изменить `title` с новым `updated_at` | Изменение применилось |
| 7 | Передать старый `updated_at` | `skipped: true`, локальная версия не затёрта |
| 8 | Передать `deleted_at` | Задача в архиве, не удалена физически |
| 9 | `GET /tasks?since=...` | Архивные записи тоже приходят (tombstones) |
| 10 | Пагинация 500+ | Нет потери задач, курсор двигается |
| 11 | Неверный токен | `401`, без утечки данных |
| 12 | Личная задача | Не видна в API (после фикса §0) |
| 13 | Round-trip: создать у нас → отправить Игорю → вернуть | Нет дубля, `external_id` стабилен |
| 14 | Повторный запуск синхронизации | Нет новых дублей |

Тестовые данные после приёмки удалить/архивировать.
