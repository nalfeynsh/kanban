# ВКС в «Моём Канбане» — скоуп следующего этапа

Статус: **запланировано, не начато**. Настоящий документ фиксирует объём, архитектурные развилки
и порядок работ, чтобы не потерять требования между сессиями.

## 1. Цель

Добавить в Канбан полноценные встречи: планирование, приглашения, календарь, аудио/видеосвязь,
демонстрацию экрана, фоны/блюр, напоминания и чат встречи с файлами.

Ориентир по функциональности: Microsoft Teams и Яндекс Телемост. Не копировать интерфейс,
а взять проверенные сценарии: «создал встречу → пригласил → участники увидели в календаре →
подключились по ссылке → общались, показывали экран, писали в чат».

## 1.1. Зафиксированные решения

- **Гости без аккаунта:** в первом релизе не нужны. Предусмотреть архитектурно возможность
  гостевых ссылок позже, но не включать в MVP.
- **Ёмкость:** жёсткий лимит первого релиза — **10 участников**. Архитектуру проектируем
  с запасом до **50**, но полноценный нагрузочный тест 50 и коммерческое расширение —
  отдельный этап после MVP.
- **Запись встреч:** нужна.
- **Чат встречи:** сохраняется после окончания встречи.
- **SFU:** облачный или self-hosted — определить по результатам spike; предварительная
  рекомендация ниже.
- **Внешние календари:** нужны **и Google Calendar, и Microsoft Outlook**.
- **Расшифровка, PSTN, мобильные приложения, трансляции** — вне первого релиза.

## 2. Функциональный объём

### 2.1. Встречи и приглашения

- [ ] Создание встречи: название, описание, дата/время начала и окончания, организатор.
- [ ] Выбор участников из команды.
- [ ] Приглашение участников; статусы `приглашён / принял / отклонил`.
- [ ] Автоматическое добавление встречи в календарь организатора и принявших участников.
- [ ] Ссылка на встречу: копирование, переход, подключение.
- [ ] Редактирование и отмена встречи; уведомление участников об изменениях.
- [ ] Отображение встреч в общем календаре отдельным слоем/цветом, не смешивая с задачами.
- [ ] Карточка встречи в календаре: участники, статус, «Подключиться», чат.

### 2.2. Аудио и видео

- [ ] Подключение к встрече по ссылке.
- [ ] Сетка участников, имя, аватар, состояние микрофона/камеры.
- [ ] Включение/выключение микрофона.
- [ ] Включение/выключение камеры.
- [ ] Выбор устройства ввода видео (камера).
- [ ] Выбор устройства ввода аудио (микрофон).
- [ ] Выбор устройства вывода аудио (наушники/колонки), где поддерживается браузером.
- [ ] Предпросмотр камеры и индикатор уровня микрофона до входа.
- [ ] Активный говорящий, список участников, состояние соединения.
- [ ] Жёсткий лимит первого релиза: **10 участников** (проверять при выдаче токена комнаты).
- [ ] Архитектурный запас до **50**: simulcast, пагинация сетки, отдельный SFU-регион.
- [ ] Полный нагрузочный тест 50 — отдельный этап перед расширением лимита, не блокирует MVP.

### 2.3. Фоны и блюр

- [ ] Несколько стандартных фонов, заложенных в систему (без загрузки своих в MVP).
- [ ] Блюр заднего фона: слабый / средний / сильный.
- [ ] Переключение «обычная камера / блюр / фон» на лету.
- [ ] Сохранение выбора пользователя между встречами (по возможности).
- [ ] Предпросмотр фона до включения камеры.

### 2.4. Демонстрация экрана

- [ ] Кнопка «Показать экран».
- [ ] Выбор источника через системный picker браузера:
  - конкретное окно;
  - весь экран;
  - конкретный монитор, если их несколько.
- [ ] Индикатор «вы показываете экран», быстрое завершение демонстрации.
- [ ] Корректное поведение, если браузер не поддерживает выбор окна/монитора.

### 2.5. Напоминания

- [ ] Напоминание за 30 минут до начала.
- [ ] Напоминание за 5 минут до начала.
- [ ] Звуковое и визуальное напоминание (тост «Встреча … через 30 минут»).
- [ ] Клик по тосту открывает встречу/карточку.
- [ ] Браузерное уведомление, если вкладка скрыта (при наличии разрешения).
- [ ] Защита от повторных напоминаний; отмена при отмене встречи.

### 2.6. Чат встречи

- [ ] Чат доступен только участникам встречи.
- [ ] Текстовые сообщения.
- [ ] Отправка файлов и документов.
- [ ] Отправка изображений с превью и открытием в просмотрщике.
- [ ] Скачивание файлов.
- [ ] Ограничения размера/типа файлов, как в существующем чате.
- [ ] История чата после завершения встречи — по правилам доступа (уточнить срок хранения).

### 2.7. Интеграция с Канбаном

- [ ] Встреча может быть связана с задачей/проектом (опционально).
- [ ] Из задачи можно создать встречу с привязкой к ней.
- [ ] В календаре встречи и задачи визуально различаются.
- [ ] Уведомления о встрече используют существующую инфраструктуру тостов/звука.

### 2.8. Запись встречи

- [ ] Индикатор «Идёт запись» для всех участников.
- [ ] Запись комнаты: сетка участников + общий звук.
- [ ] Сохранение записи в защищённое хранилище.
- [ ] Список записей у организатора/участников.
- [ ] Просмотр/скачивание записи только тем, у кого есть доступ к встрече.
- [ ] Политика хранения и удаления записей.
- [ ] Согласие участников/уведомление о записи.

Запись 50 участников — ресурсоёмкая операция. Для первого релиза записывать 10,
архитектурно проверить 50 через Egress/SFU.

### 2.9. Внешние календари

- [ ] Подключение Google Calendar через OAuth.
- [ ] Подключение Microsoft Outlook / Microsoft Graph через OAuth.
- [ ] Создание события во внешнем календаре организатора.
- [ ] Приглашение участников с join-ссылкой.
- [ ] Обновление/отмена события при изменении встречи.
- [ ] Выбор календаря, если у пользователя их несколько.
- [ ] Обработка отзыва доступа/истечения токена.
- [ ] Fallback `.ics` для участников без подключённого календаря.

**Граница MVP:** приложение создаёт событие и приглашения через календарь организатора.
Двусторонняя синхронизация (изменения в Google/Outlook → Канбан) — отдельный этап.

## 3. Что не входит в первый релиз

- расшифровка аудио/видео;
- телефонный доступ (PSTN);
- отдельные мобильные приложения;
- трансляции на внешние платформы;
- гости без аккаунта;
- двусторонняя синхронизация с Google/Outlook (в MVP — создание событий и приглашений).

## 4. Архитектурные варианты

### 4.1. WebRTC mesh

Каждый участник отправляет поток каждому. Подходит для 1:1 и 2–3 человек.
Для 10 участников это 9 исходящих потоков на клиента — высокая нагрузка на CPU/канал,
не рекомендуется как основной вариант.

### 4.2. SFU — рекомендуемый вариант

SFU принимает поток один раз и раздаёт участникам. Кандидаты:

- LiveKit (Cloud или self-hosted);
- Jitsi (self-hosted/8×8);
- Daily;
- 100ms;
- Whereby Embedded.

Для проекта важны:

- стоимость при 10 участниках;
- TURN/STUN из коробки;
- поддержка браузеров;
- возможность self-host;
- SDK для React;
- screen share и виртуальные фоны/блюр;
- политика хранения данных.

**Предварительная рекомендация:** **self-hosted LiveKit в российском облаке** (SFU + Egress)
как основной вариант: контроль данных, запись, независимость от зарубежных тарифов и доступности.
LiveKit Cloud — быстрый старт для spike и запасной вариант, если self-host окажется слишком
дорогим в эксплуатации. Jitsi + Jibri — альтернатива, но запись и масштабирование до 50
требуют больше инфраструктурной работы.

Окончательное решение — после spike-проверки:
- стоимость 10 и 50 участников;
- доступность из РФ и задержка;
- качество записи 10/50;
- TURN/STUN;
- требования к хранению данных.

Layero Runtime (`server.js`) **не может быть SFU**: он отдаёт статику и проксирует Supabase.
Медиа-сервер должен жить отдельно (облако/SFU или отдельная VM).

Материалы для spike (тарифы и масштабирование проверить на актуальную дату):
- [LiveKit: per-second metering](https://livekit.com/blog/introducing-per-second-metering-for-livekit)
- [LiveKit: sizing self-hosted Egress](https://community.livekit.io/t/production-sizing-for-self-hosted-track-egress/1858)
- [Jitsi: scaling и Jibri](https://community.jitsi.org/t/how-to-scale-jitsi-meet-for-500-1000-users-with-video-bridges-and-jibri/139418/2)
- [Daily: pricing](https://www.daily.co/pricing/video-sdk/)

### 4.3. Supabase

- `meetings`, `meeting_participants`, `meeting_messages`, `meeting_attachments`;
- RLS: доступ только участникам/организатору;
- Storage bucket для файлов встречи;
- Realtime — для статусов приглашений, чата и напоминаний;
- календарь — отдельный слой событий.

### 4.4. Ссылка и доступ

MVP: только авторизованные сотрудники команды.
Гости по ссылке без аккаунта — отдельное решение: нужны одноразовые токены, ограничение по времени,
защита от перебора и правила модерации. Не смешивать с текущей invite-only регистрацией.

### 4.5. Запись

- LiveKit Egress (room composite) → S3-совместимое хранилище;
- запись комнаты: сетка + аудио;
- метаданные записи в Supabase, доступ по RLS к встрече;
- отдельный bucket/папка, signed URL, запрет публичного доступа;
- индикатор записи и согласие участников;
- хранение и удаление — по политике (уточнить срок).

### 4.6. Google Calendar и Outlook

- OAuth 2.0 на пользователя; refresh token хранится на сервере (Layero Node или Supabase Vault),
  не в браузере;
- Google Calendar API: `events.insert/update/delete`, `sendUpdates=all`;
- Microsoft Graph: `/me/events`, `attendees`, `onlineMeeting`/join URL в описании;
- приложение создаёт событие в календаре организатора и рассылает приглашения участникам;
- для участников без внешнего календаря — `.ics`;
- нужны регистрации приложений Google Cloud и Azure AD, redirect URI и проверка scopes;
- двусторонняя синхронизация — позже (webhooks/change tokens, конфликт-резолюция).

**Важно:** если приглашения отправляет Google/Outlook организатора, участники получают
письмо-приглашение. Это проще и надёжнее, чем писать события в календарь каждого участника
по отдельности.

## 5. Технические риски

| Риск | Влияние | Решение |
|---|---|---|
| Mesh на 10 участников | Лаги, высокая нагрузка | SFU |
| Масштабирование до 50 | Нагрузка на SFU и клиенты | нагрузочный тест, simulcast, пагинация |
| Запись 10–50 | CPU/диск, стоимость Egress | отдельный Egress, лимиты, хранение |
| Запись и согласие | Юридический риск | индикатор, согласие, политика |
| OAuth Google/Outlook | Истечение токенов, отзыв доступа | refresh, обработка ошибок, повторное подключение |
| Разные календари | Разное поведение приглашений | Google API + Graph + `.ics` fallback |
| Нет TURN | Часть пользователей не подключится | TURN в SFU/облаке |
| Layero не медиа-сервер | Нельзя запустить SFU в текущем runtime | Отдельный сервис |
| Браузеры по-разному поддерживают screen share | Не все источники доступны | Fallback + подсказки |
| Блюр фона требует сегментации | CPU/качество | MediaPipe/WebGL, тест на слабых ПК |
| Напоминания только при открытой вкладке | Можно пропустить | Web Push — отдельная задача, либо принять ограничение |
| Файлы в чате | Безопасность/размер | Bucket, RLS, лимиты, проверка типа |
| Гости по ссылке | Утечка доступа | Одноразовые токены, срок жизни, лобби |
| Стоимость SFU | Бюджет | Сравнить тарифы 10/50, self-host vs cloud |

## 6. Этапы работ

### Этап 0. Исследование и spike — 1–2 дня

- [ ] Сравнить Teams / Яндекс Телемост / LiveKit / Jitsi / Daily по чек-листу.
- [ ] Проверить доступность SFU из РФ и качество связи.
- [ ] Проверить `getUserMedia`, `getDisplayMedia`, `enumerateDevices`, `setSinkId` в целевых браузерах.
- [ ] Проверить блюр/фон на среднем ноутбуке.
- [ ] Зафиксировать бюджет и выбранный SFU.

### Этап 1. Встречи, приглашения, календарь — 3–5 дней

- [ ] Миграция таблиц встреч и участников.
- [ ] Создание/редактирование/отмена встречи.
- [ ] Приглашения и статусы.
- [ ] Слой встреч в календаре.
- [ ] Ссылка на встречу.
- [ ] Напоминания 30/5 минут.

### Этап 2. Аудио/видео — 5–8 дней

- [ ] Подключение к комнате SFU.
- [ ] Сетка участников, mic/cam toggle.
- [ ] Выбор устройств ввода/вывода.
- [ ] Предпросмотр и тест устройств.
- [ ] Обработка ошибок доступа/сети.

### Этап 3. Фоны, блюр, screen share — 4–6 дней

- [ ] Стандартные фоны.
- [ ] Блюр 3 уровня.
- [ ] Демонстрация окна/экрана/монитора.
- [ ] Индикаторы и завершение демонстрации.

### Этап 4. Чат встречи и файлы — 3–4 дня

- [ ] Таблица сообщений встречи.
- [ ] Текст, файлы, изображения.
- [ ] Скачивание/просмотр.
- [ ] RLS и лимиты.
- [ ] Хранение истории после завершения встречи.

### Этап 5. Запись встреч — 4–6 дней

- [ ] Egress/SFU-запись.
- [ ] Индикатор записи и согласие.
- [ ] Хранение и список записей.
- [ ] Доступ, signed URL, удаление.
- [ ] Тест записи 10 участников; проверка запаса на 50.

### Этап 6. Google Calendar и Outlook — 5–8 дней

- [ ] OAuth Google/Microsoft, хранение refresh token.
- [ ] Создание/обновление/отмена события.
- [ ] Приглашения участникам.
- [ ] `.ics` fallback.
- [ ] Обработка отзыва доступа.

### Этап 7. Стабилизация и масштаб — 4–6 дней

- [ ] Тесты на 10 участниках.
- [ ] Проверить архитектурный запас до 50 (design review, лимиты SFU).
- [ ] Полный нагрузочный тест 50 — перед расширением лимита, отдельным этапом.
- [ ] Слабый интернет, переподключение.
- [ ] Мобильные браузеры.
- [ ] Политика хранения и удаления.
- [ ] Документация для пользователей.

**Итого:** ориентировочно **5–8 недель** с записью, внешними календарями и проверкой
масштабирования до 50. Оценка уточняется после spike и выбора SFU.

## 7. Критерии готовности MVP

- [ ] Двое и более сотрудников создают встречу и подключаются по ссылке.
- [ ] Участники видят встречу в календаре и получают приглашение.
- [ ] Работают mic/cam toggle и выбор устройств.
- [ ] Работает screen share с выбором окна/экрана.
- [ ] Работают стандартные фоны и 3 уровня блюра.
- [ ] Напоминания приходят за 30 и 5 минут с тостом и звуком.
- [ ] В чате встречи можно отправить текст, файл и изображение; файл скачивается.
- [ ] Чат и встреча доступны только участникам.
- [ ] Чат сохраняется после окончания встречи.
- [ ] Запись встречи создаётся, доступна участникам и защищена от публичного доступа.
- [ ] Встреча создаётся в Google Calendar и Outlook организатора, участники получают приглашение.
- [ ] Архитектура готова к расширению до 50 (лимит 10 в MVP, расширение — отдельным этапом).
- [ ] Нет критических утечек доступа и данных.

## 8. Открытые вопросы к заказчику

1. Сколько хранить записи встреч (30 дней, год, бессрочно)?
2. Нужна ли двусторонняя синхронизация с Google/Outlook или достаточно создания событий
   и приглашений из Канбана?
3. Кто может начинать/останавливать запись: организатор, администратор, все?
4. Кто модерирует встречу: организатор, администратор, все?
5. Нужны ли гости без аккаунта в следующем этапе после MVP?
6. Есть ли требования к хранению данных и записей только внутри РФ?
7. Какой бюджет на SFU/Egress в месяц?
