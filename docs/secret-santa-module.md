# Тайный Санта — техническое задание на отдельный модуль

Статус: проект ТЗ, не реализовано  
Дата: 18.11.2026  
Контекст: «Мой Канбан», React + Supabase, проекты и RLS уже есть.

---

## 1. Краткое решение

«Тайный Санта» делается **отдельным модулем проекта**, а не частью задач или профилей.

Ключевые решения:

- все таблицы имеют префикс `secret_santa_`;
- весь frontend-код лежит в `src/features/secret-santa/`;
- модуль включается флагом `secret_santa`;
- в основной код добавляются только точка входа, флаг и ленивая загрузка модуля;
- жеребьёвка выполняется на сервере, участник видит только свою пару;
- организатор не видит пары — он может только запустить/сбросить жеребьёвку;
- удаление модуля — одна миграция и удаление одной папки.

Ориентир по MVP: **5–7 рабочих дней**.  
Расширенная версия с анонимными сообщениями, запланированной жеребьёвкой и раскрытием: **8–12 дней**.

## 3. Границы модуля

### 3.1. Входит в MVP

- создание игры в проекте;
- участие сотрудников проекта;
- пожелания к подарку;
- диапазон бюджета: минимум и максимум;
- дата жеребьёвки и дата обмена;
- исключения;
- жеребьёвка на сервере;
- просмотр только своей пары;
- повторная жеребьёвка организатором;
- удаление/отмена игры;
- уведомления о жеребьёвке;
- feature flag;
- изолированные таблицы и удаление модуля.

### 3.2. Phase 2

- анонимные вопросы получателю и ответы;
- структурированный вишлист со ссылками и ценой;
- резервирование подарков;
- запланированная автоматическая жеребьёвка;
- прошлогодние пары как автоматическое исключение;
- точечная замена одной пары;
- печатные карточки/PDF;
- внешние гости по ссылке;
- адрес доставки, видимый только дарителю.

### 3.3. Не входит

- денежные переводы и оплата подарков;
- маркетплейс подарков;
- доставка и логистика;
- публичные группы вне проектов;
- интеграция с Wildberries/Ozon и т.п.;
- email-рассылки (только внутренние уведомления).

## 4. Роли и доступ

### 4.1. Роли модуля

| Роль | Кто | Права |
|---|---|---|
| Организатор | владелец проекта, project manager, admin, manager, deputy | создать игру, редактировать, добавлять участников, задавать исключения, запускать/сбрасывать жеребьёвку, отменять игру |
| Участник | любой участник проекта | вступить, заполнить пожелания, видеть свою пару, получать уведомления |
| Наблюдатель | участник проекта, не вступивший в игру | видеть факт игры и список участников, но не пары |

Важно: **организатор не должен видеть назначения**. Он видит только статус «жеребьёвка проведена» и количество участников.

### 4.2. Серверные проверки

Использовать существующие функции проекта:

- `is_admin()`;
- `can_manage_project(project_id)`;
- членство в `project_members`.

Правило:

```text
can_manage_secret_santa(game_id) =
  is_admin()
  or can_manage_project(game.project_id)
```

Правило участия:

```text
can_participate(game_id) =
  exists project_members(project_id, auth.uid())
```

## 5. Пользовательские сценарии

### 5.1. Создание игры

1. Организатор открывает проект.
2. Нажимает «Тайный Санта».
3. Видит список игр проекта.
4. Нажимает «Создать игру».
5. Указывает:
   - название;
   - описание/правила;
   - бюджет: минимум и максимум (оба поля необязательны);
   - дату жеребьёвки;
   - дату обмена;
   - дату раскрытия (опционально);
   - включать ли прошлогодние пары в исключения.
6. Создаёт игру в статусе `draft`.
7. Нажимает «Открыть набор» → статус `collecting`.

### 5.2. Участие

1. Участник проекта открывает игру.
2. Нажимает «Участвовать».
3. Заполняет пожелания:
   - текст;
   - ссылка на вишлист;
   - размер/предпочтения (опционально).
4. Может выйти из игры до жеребьёвки.
5. После жеребьёвки выйти нельзя — только организатор может отменить игру.

### 5.3. Исключения

Организатор добавляет пары:

- «А не дарит Б»;
- «Б не дарит А».

В интерфейсе проще указывать одну пару как **взаимное исключение**. В БД можно хранить одну каноническую пару `(a,b)`, где `a < b`, и трактовать её как двустороннюю.

Валидация:

- оба участника из этой игры;
- нельзя исключить самого себя;
- нельзя дублировать;
- нельзя создать ситуацию, где жеребьёвка невозможна.

### 5.4. Жеребьёвка

1. Организатор нажимает «Провести жеребьёвку».
2. Сервер проверяет:
   - минимум 3 участника;
   - все участники активны;
   - нет невозможных ограничений.
3. Сервер строит назначения.
4. Назначения сохраняются.
5. Каждому участнику создаётся уведомление.
6. Участник видит только своего получателя и его пожелания.
7. Организатор видит «Жеребьёвка проведена», но не пары.

### 5.5. Просмотр своей пары

Участник видит:

- имя получателя;
- аватар;
- пожелания;
- ссылку на вишлист;
- диапазон бюджета;
- дату обмена;
- кнопку «Написать анонимно» (phase 2).

Если участник не в игре — экран «Вы не участвуете».

### 5.6. Раскрытие

После `reveal_at`:

- участник может нажать «Кто был моим Сантой?»;
- сервер возвращает имя дарителя только после даты раскрытия;
- до этого даритель не раскрывается.

### 5.7. Отмена и удаление

- Организатор может отменить игру в любом статусе.
- Отмена не удаляет данные сразу; статус `cancelled`.
- Удаление игры — только организатор, с подтверждением.
- При удалении игры удаляются участники, исключения, назначения и сообщения.
- Проект и задачи не затрагиваются.

## 7. Модель данных

Все таблицы — в `public`, с префиксом `secret_santa_`, чтобы не менять существующие сущности.

### 7.1. `secret_santa_games`

```sql
create table public.secret_santa_games (
  id uuid primary key default gen_random_uuid(),
  project_id uuid not null references public.projects(id) on delete cascade,
  title text not null,
  description text,
  rules text,
  budget_min numeric(12,2),
  budget_max numeric(12,2),
  currency text not null default 'RUB',
  check (budget_min is null or budget_min >= 0),
  check (budget_max is null or budget_max >= 0),
  check (budget_min is null or budget_max is null or budget_min <= budget_max),
  status text not null default 'draft'
    check (status in ('draft','collecting','drawn','exchange','completed','cancelled')),
  draw_at timestamptz,
  exchange_at timestamptz,
  reveal_at timestamptz,
  drawn_at timestamptz,
  drawn_by uuid references public.profiles(id),
  created_by uuid not null references public.profiles(id),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
```

Индексы:

- `(project_id, created_at desc)`;
- `(status)`.

### 7.2. `secret_santa_participants`

```sql
create table public.secret_santa_participants (
  id uuid primary key default gen_random_uuid(),
  game_id uuid not null references public.secret_santa_games(id) on delete cascade,
  user_id uuid not null references public.profiles(id) on delete cascade,
  wishlist text,
  wishlist_url text,
  preferences text,
  joined_at timestamptz not null default now(),
  unique (game_id, user_id)
);
```

Пожелания видны участникам игры. Если нужна приватность — phase 2, только получателю.

### 7.3. `secret_santa_exclusions`

```sql
create table public.secret_santa_exclusions (
  id uuid primary key default gen_random_uuid(),
  game_id uuid not null references public.secret_santa_games(id) on delete cascade,
  participant_a uuid not null references public.secret_santa_participants(id) on delete cascade,
  participant_b uuid not null references public.secret_santa_participants(id) on delete cascade,
  created_by uuid not null references public.profiles(id),
  created_at timestamptz not null default now(),
  check (participant_a < participant_b),
  unique (game_id, participant_a, participant_b)
);
```

Трактовка: `a` и `b` не могут дарить друг другу в обе стороны.

### 7.4. `secret_santa_assignments`

```sql
create table public.secret_santa_assignments (
  id uuid primary key default gen_random_uuid(),
  game_id uuid not null references public.secret_santa_games(id) on delete cascade,
  giver_participant_id uuid not null references public.secret_santa_participants(id) on delete cascade,
  recipient_participant_id uuid not null references public.secret_santa_participants(id) on delete cascade,
  created_at timestamptz not null default now(),
  unique (game_id, giver_participant_id),
  unique (game_id, recipient_participant_id),
  check (giver_participant_id <> recipient_participant_id)
);
```

### 7.5. `secret_santa_messages` (phase 2)

```sql
create table public.secret_santa_messages (
  id uuid primary key default gen_random_uuid(),
  game_id uuid not null references public.secret_santa_games(id) on delete cascade,
  giver_participant_id uuid not null references public.secret_santa_participants(id) on delete cascade,
  recipient_participant_id uuid not null references public.secret_santa_participants(id) on delete cascade,
  body text not null,
  created_at timestamptz not null default now(),
  read_at timestamptz
);
```

Для MVP таблицу можно не создавать.

### 7.6. Связь с уведомлениями

Использовать существующую таблицу `notifications`:

```text
kind = 'secret_santa'
entity_type = 'secret_santa_game'
entity_id = game_id
project_id = game.project_id
```

Не добавлять в `notifications` новый FK на игру, чтобы удаление модуля не требовало менять основную таблицу.

## 8. Жеребьёвка

### 8.1. Алгоритм

На сервере, в `security definer` RPC `secret_santa_draw(p_game_id uuid)`.

1. Проверить, что вызывающий — организатор.
2. Проверить статус `collecting`.
3. Загрузить участников.
4. Проверить минимум 3 участника.
5. Построить граф запретов:
   - self;
   - исключения;
   - опционально прошлогодние пары.
6. Найти случайное совершенное паросочетание:
   - перемешать получателей;
   - проверить ограничения;
   - при конфликте — backtracking;
   - ограничить число попыток.
7. Если решения нет — вернуть понятную ошибку.
8. Удалить старые назначения (при повторной жеребьёвке).
9. Вставить новые назначения.
10. Обновить игру: `status='drawn'`, `drawn_at`, `drawn_by`.
11. Создать уведомления участникам.
12. Вернуть только `{ ok, participants }`, без пар.

### 8.2. Почему не на клиенте

Если считать пары в браузере, все назначения окажутся в памяти клиента, и секретность будет условной. Жеребьёвка должна быть на сервере.

### 8.3. Просмотр своей пары

RPC `secret_santa_my_assignment(p_game_id uuid)`:

- находит participant текущего пользователя;
- находит assignment, где он giver;
- возвращает данные получателя и его пожелания;
- не возвращает остальные назначения.

### 8.4. Раскрытие

RPC `secret_santa_reveal(p_game_id uuid)`:

- проверяет, что `reveal_at <= now()`;
- находит assignment, где текущий пользователь — recipient;
- возвращает имя giver.

До `reveal_at` функция возвращает `null`.

## 9. RLS и безопасность

### 9.1. Политики

`secret_santa_games`:

- select: участник проекта или admin;
- insert/update/delete: организатор.

`secret_santa_participants`:

- select: участник проекта;
- insert: только self через RPC;
- update: self (wishlist) или организатор;
- delete: self до жеребьёвки или организатор.

`secret_santa_exclusions`:

- select/insert/delete: организатор.

`secret_santa_assignments`:

- select: только `giver_participant_id` текущего пользователя;
- insert/update/delete: только через `security definer` RPC;
- организатор **не** получает select-политику на все строки.

`secret_santa_messages` (phase 2):

- select: только recipient;
- insert: только giver своей пары через RPC.

### 9.2. Обязательные проверки

- нельзя вступить в игру чужого проекта;
- нельзя добавить участника, не являющегося членом проекта;
- нельзя провести жеребьёвку при < 3 участниках;
- нельзя изменить состав после жеребьёвки без сброса;
- нельзя посмотреть чужую пару через прямой select;
- нельзя получить пары организатору через UI.

### 9.3. Что не должно попадать в клиент

- полный список назначений;
- service role key;
- чужие wishlist-ссылки, если решим их скрывать;
- email/телефоны, если не нужны.

## 10. Изоляция и удаление

### 10.1. Структура кода

```text

```

### 10.2. Точки подключения к основному коду

Максимум 4 точки + одна ветка обработчика уведомлений:

1. `lib/features.js` — добавить `secret_santa` в список флагов.
2. `FeatureFlagsPanel.jsx` — флаг появится автоматически, если панель строится из реестра.
3. `Header.jsx` или меню проекта — кнопка «Тайный Санта» при включённом флаге.
4. `App.jsx` — lazy import и состояние открытия.
5. `App.handleOpenNotification` — переход к игре по уведомлению (если включаем уведомления в MVP).

Если хочется ещё меньше связности: кнопку можно поместить в `ProjectsModal`, а не в шапку.

Правило для разработки: модуль может импортировать только `supabaseClient`, `Avatar` и общие UI-утилиты. Основной код **не должен импортировать внутренние файлы модуля**, кроме одной ленивой точки входа.

### 10.3. Флаг

```text
features.secret_santa = false by default
```

Выключение:

- кнопка исчезает;
- lazy chunk не загружается;
- данные остаются;
- уведомления по модулю не создаются.

Удаление:

1. Удалить папку `src/features/secret-santa/`.
2. Убрать lazy import и кнопку.
3. Убрать флаг из реестра.
4. Применить миграцию `drop table ... cascade`.
5. Удалить уведомления `kind='secret_santa'`, если нужно.

Основные таблицы не менялись — откат безопасен.

Миграция модуля: `supabase/migrations/037_secret_santa.sql`.  
Откат: `supabase/migrations/037_secret_santa_rollback.sql` (не применять в обычном деплое).

## 11. Интерфейс

### 11.1. Точка входа

Вариант A (рекомендуемый): кнопка **«Тайный Санта»** в шапке проекта, иконка подарка.  
Вариант B: пункт в меню проекта.  
Вариант C: отдельная вкладка внутри проекта.

Для MVP достаточно модального окна, чтобы не менять маршрутизацию.

### 11.2. Экран списка игр

- список игр проекта;
- статус, дата обмена, число участников;
- кнопка «Создать игру» (организатор);
- пустое состояние.

### 11.3. Экран игры

Шапка:

- название;
- статус;
- диапазон бюджета;
- даты;
- кнопки «Участвовать» / «Выйти»;
- организаторские кнопки.

Вкладки:

1. **Обзор** — правила, участники, даты.
2. **Мои пожелания** — текст, ссылка, предпочтения.
3. **Участники** — список, кто участвует.
4. **Исключения** — только организатор.
5. **Моя пара** — после жеребьёвки.

### 11.4. Организаторский блок

- «Открыть набор»;
- «Провести жеребьёвку»;
- «Перепровести жеребьёвку»;
- «Отменить игру»;
- «Удалить игру».

Перед жеребьёвкой показывать:

- участников: N;
- исключений: M;
- предупреждение, что после жеребьёвки состав меняется только через сброс.

### 11.5. Участник после жеребьёвки

Карточка:

```text
Ваш получатель: Иван Иванов
Пожелания: ...
Ссылка на вишлист: ...
Бюджет: 1 000–2 000 ₽
Обмен: 25 декабря
```

Кнопка «Написать анонимно» — phase 2.

### 11.6. Бюджет

Бюджет задаётся как **диапазон**, а не одно число:

- «от» — минимальная комфортная сумма;
- «до» — максимальная сумма;
- оба поля необязательны;
- можно указать только «до» или только «от»;
- валюта — по умолчанию рубль;
- бюджет носит рекомендательный характер и не блокирует жеребьёвку.

UI:

```text
Бюджет подарка
[ от: 1 000 ₽ ]  —  [ до: 2 000 ₽ ]
Подсказка: «Можно не указывать»
```

Пресеты для быстрого выбора: 500, 1 000, 2 000, 3 000, 5 000 ₽.

Отображение:

- `от 1 000 ₽` — если задан только минимум;
- `до 2 000 ₽` — если задан только максимум;
- `1 000–2 000 ₽` — если заданы оба;
- `Бюджет не указан` — если пусто.

Валидация:

- значения не отрицательные;
- `минимум <= максимум`;
- пустые значения допустимы;
- при ошибке показывать сообщение у полей, а не блокировать весь экран.

## 12. Уведомления

MVP:

- после жеребьёвки — уведомление каждому участнику;
- за 3 дня до обмена — напоминание (можно phase 2);
- при отмене игры — уведомление участникам.

Использовать существующий центр уведомлений:

```text
kind: secret_santa
title: «Тайный Санта: жеребьёвка проведена»
body: название игры
entity_type: secret_santa_game
entity_id: game_id
```

В `App.handleOpenNotification` добавить ветку:

```text
if (notification.entity_type === 'secret_santa_game') {
  openSecretSanta(notification.entity_id);
}
```

Это единственная правка обработчика уведомлений. Если не хотим трогать `App`, в MVP уведомления можно показывать только внутри модуля.

## 13. Крайние случаи

| Ситуация | Поведение |
|---|---|
| Меньше 3 участников | Жеребьёвка запрещена, понятная ошибка |
| Исключения делают жеребьёвку невозможной | Ошибка «Ослабьте ограничения», пары не создаются |
| Участник вышел после жеребьёвки | Запрещено; только отмена/сброс организатором |
| Новый участник после жеребьёвки | Запрещено; нужен сброс |
| Организатор пытается посмотреть пары | RLS не отдаёт; UI не показывает |
| Участник не заполнил пожелания | Разрешить, но показать предупреждение |
| Две игры в проекте | Разрешить; одна активная — рекомендация, не ограничение |
| Удаление проекта | Каскадное удаление игр и данных |
| Выключение флага | Данные сохраняются, модуль скрыт |
| Повторная жеребьёвка | Старые назначения удаляются, создаются новые, уведомления повторно |
| Раскрытие до даты | Запрещено |
| Часовой пояс | Все даты в `timestamptz`, отображение в Europe/Moscow |

## 14. Критерии приёмки MVP

1. Организатор создаёт игру в проекте.
2. Участник проекта вступает и сохраняет пожелания.
3. Организатор задаёт бюджет: оба поля, только «от», только «до» или пусто; `минимум <= максимум`.
4. Организатор добавляет исключение.
5. Жеребьёвка проходит при 3+ участниках.
6. Каждый участник видит только своего получателя.
7. Участник не может запросить чужую пару через API.
8. Организатор не видит пары.
9. При невозможных исключениях жеребьёвка не создаёт частичные данные.
10. Повторная жеребьёвка заменяет пары.
11. Игра отменяется и удаляется без влияния на задачи.
12. Флаг выключает модуль, данные остаются.
13. Удаление миграцией удаляет только `secret_santa_*`.
14. Уведомление о жеребьёвке приходит участникам.
15. Модуль не меняет `tasks`, `columns`, `profiles`, `projects`.

## 16. Риски

| Риск | Вероятность | Влияние | Снижение |
|---|---|---|---|
| Утечка пар через API или клиент | Средняя | Высокое | RLS только на свою пару, RPC без списка, тест «чужая пара недоступна» |
| Невозможная жеребьёвка из-за исключений | Средняя | Среднее | Валидация до вставки, backtracking, понятная ошибка, откат без частичных данных |
| Участник вышел после жеребьёвки | Средняя | Среднее | Запрет выхода после `drawn`; только отмена/сброс |
| Организатор хочет видеть пары | Высокая | Высокое | Не давать такой возможности; объяснить в UI, что это защита сюрприза |
| Модуль начнёт «протекать» в основной код | Средняя | Среднее | Папка `features/secret-santa`, максимум 5 точек входа, code review |
| Удаление оставит данные | Низкая | Среднее | Все таблицы с префиксом, rollback-миграция, чек-лист удаления |
| Уведомления останутся после удаления | Низкая | Низкое | Очистка `kind='secret_santa'` в rollback |
| Дата/часовой пояс отображается неверно | Низкая | Низкое | `timestamptz` + Europe/Moscow, тест на границе дня |

## 18. Решения по умолчанию

Так как детальных требований пока нет, предлагаются такие решения:

1. Только сотрудники проекта, без внешних гостей.
2. Одна игра может быть активной; старые игры остаются в истории.
3. Бюджет задаётся диапазоном «от/до» и необязателен.
4. Пожелания — свободный текст + ссылка.
5. Исключения — взаимные.
6. Жеребьёвка запускается вручную.
7. Раскрытие — по дате, phase 2.
8. Уведомления — только внутренние.
9. Никаких email и адресов доставки в MVP.
10. Все данные удаляются вместе с проектом.

## 20. Что нужно подтвердить перед реализацией

1. Игра только для сотрудников проекта или нужны внешние гости?
2. Нужен ли бюджет только «до», или всегда диапазон «от/до»? По умолчанию — оба поля, оба необязательны.
3. Нужны ли анонимные сообщения в первой версии?
4. Нужна ли автоматическая жеребьёвка по дате?
5. Нужны ли прошлогодние пары как исключения?
6. Нужно ли раскрытие дарителя?
7. Показывать ли пожелания всем участникам или только дарителю?
8. Одна активная игра на проект или несколько?

Если ответов нет, реализовывать по решениям из раздела 17.
