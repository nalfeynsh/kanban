# Командная доска: анализ Miro / Контур.Толк и план разработки

Дата: 23.11.2026. Статус: анализ + MVP-разработка.

## 1. Что смотрели

### Miro

Miro — самостоятельный продукт для командной работы на бесконечном холсте.
Ключевые возможности, релевантные нам:

- бесконечный холст, масштаб, миникарта, фреймы;
- стикеры, текст, фигуры, стрелки и «умные» коннекторы;
- карандаш, маркер, ластик;
- изображения, документы, видео, таблицы, презентации;
- совместное редактирование в реальном времени, курсоры участников;
- режим «следить за участником» (follow): клик по аватару — viewport
  повторяет перемещение коллеги;
- права: edit / comment / view, ссылки на доску и отдельные фреймы;
- таймер, анонимное голосование, реакции, комментарии;
- AI: генерация, группировка стикеров, майнд-карты;
- интеграции со Slack, Teams, Google Meet, Jira и др.

### Контур.Толк

Толк развивает интерактивные доски как часть встреч:

- доска внутри созвона;
- карандаш, текст, стикеры, фигуры, изображения, стрелки, ластик;
- создатель может передать права редактирования всем участникам,
  доступ сохраняется после встречи;
- доски используются для схем, заметок и совместной работы во время обсуждения.

### Вывод по конкурентам

Miro — эталон глубины и экосистемы. Толк — пример доски, встроенной в встречу
и заточенной на быстрый старт без обучения.

Наша ниша: доска **внутри проектной команды Канбана**, связанная с задачами,
проектами и Гантом, без отдельного аккаунта и без видео в первой версии.

## 2. Можно ли развивать доску и медиасервер параллельно?

Да. Это два независимых контура:

| Контур | Зависимости | Что нужно |
|---|---|---|
| Командная доска | Supabase Postgres, Realtime, Storage, браузер | этот трек |
| Медиасервер ВКС | WebRTC/SFU, VPS/домен/TLS, порты | отдельный трек |

Общие точки:

- одна авторизация и членство в проекте;
- кнопка «Доска» в встрече (позже);
- ссылки на артефакты доски из чата/задачи.

Доска не должна ждать медиасервер: она работает асинхронно и в realtime
через Supabase. Видео в доске не требуется. Это позволяет запустить доску
раньше, чем будет готов SFU.

Риск параллельной разработки — не технический, а продуктовый: две большие
ветки могут конкурировать за время одной команды. Поэтому доску делаем
итерациями, а медиасервер остаётся отдельным треком со своим Definition of Done.

## 3. Архитектура MVP

### Модель

- `boards` — одна доска на проект (`project_id` уникален), название,
  настройки, режим редактирования.
- `board_objects` — объекты холста:
  - `sticky` — стикер;
  - `text` — текстовый блок;
  - `shape` — прямоугольник/эллипс/ромб;
  - `connector` — связь между объектами;
  - `drawing` — свободный рисунок;
  - `image` — изображение;
  - `frame` — фрейм для группировки и ссылки.
  Позиция/размер/поворот, `data` JSONB, z-index, автор.
- `board_comments` — комментарии к точке/объекту.
- `board_votes` — голоса за объект (анонимно на UI).
- `board_presence` не хранится в БД: Supabase Realtime Presence.
- Медиа — Supabase Storage, bucket `board-media`.

### Realtime

- Postgres Changes для `board_objects`, `board_comments`, `board_votes`.
- Presence для курсоров, имени, цвета и follow-сессии.
- Broadcast для промежуточных drag-событий и реакций.
- Конфликты MVP: last-write-wins по `updated_at`; версионирование и CRDT —
  следующий этап, если появятся одновременные сложные правки.

### Права

- доступ к доске наследуется от проекта;
- `boards.edit_mode`:
  - `all` — все участники проекта редактируют;
  - `managers` — редактируют админ/руководитель/ответственный, остальные смотрят
    и комментируют.
- Владелец/админ всегда редактирует.

### Ссылки на фреймы

- у фрейма есть стабильный `id`;
- ссылка вида `/board/<boardId>?frame=<frameId>`;
- при открытии камера центрируется на фрейме;
- ссылку можно скопировать из панели фрейма;
- позже — публичная ссылка только на фрейм и экспорт PNG/PDF.

## 6. Решения по умолчанию

- Одна бесконечная доска на проект.
- Без видео и без встроенного медиасервера.
- Real-time через Supabase, без отдельного WebSocket-сервера.
- BPMN — фигуры + коннекторы + шаблон, без строгого BPMN-валидатора.
- AI — следующий этап, чтобы не зависеть от внешнего API в MVP.

## 7. Риски

1. **Производительность DOM/SVG** при тысячах объектов. MVP рассчитан на
   десятки–сотни объектов; дальше — виртуализация и canvas-рендер.
2. **Конфликты одновременного drag.** Last-write-wins; для сложных сценариев
   нужен CRDT (Yjs) или серверная блокировка.
3. **Права на уровне объектов.** В MVP права на доску; точечные права на
   объекты — позже.
4. **Realtime-лимиты Supabase.** Следить за количеством подключений и
   частотой broadcast; курсоры throttle 50–100 мс.
5. **Внешние AI/LLM.** Не включаем в MVP, чтобы не блокировать запуск.
