# AGENTS.md — «Мой Канбан»

Файл агента. Здесь фиксируются **все требования** (из handoff и от заказчика), решения и статус.
Обновлять этот файл при каждом изменении объёма работ.

## 1. Проект

| Параметр | Значение |
|---|---|
| Назначение | Канбан-доска + календарь + файлы/ссылки, командная работа до 10 человек |
| Frontend | React 19 + Vite 8 |
| Стили | Tailwind CSS v4 (`@tailwindcss/vite`), `darkMode: class` |
| DnD | `@dnd-kit/core` + `@dnd-kit/sortable` |
| Редактор | TipTap (StarterKit, Underline, Link, Placeholder) |
| Календарь | FullCalendar 6 (dayGrid, timeGrid, interaction) |
| Backend | Supabase (Postgres, Auth, Storage, RLS) |
| Production | https://kanban.layero.app/ |
| Репозиторий | https://github.com/nalfeynsh/kanban (`main`) |

### Команды

```bash
npm install --legacy-peer-deps
npm run dev      # http://localhost:5173
npm run build    # dist/
npm run lint
```

## 2. Требования заказчика (актуальный backlog)

Легенда: `[x]` сделано, `[~]` сделано в UI с требованием миграции БД, `[ ]` не начато.

### Баги

- [x] **Модалка задачи: случайное закрытие, даты и архив.** Клик по пустому месту больше не закрывает
  карточку: выход только через «Сохранить и закрыть», крестик или `Esc`. «Начало»/«Срок» — одно поле
  с итогом `дд.мм.гг чч:мм`; по клику раскрывается дата + необязательное время, пресеты
  «Сегодня / Завтра / +3 дня / Очистить» и явная кнопка «Готово». После выбора дня календарь
  закрывается сам, время — следующий шаг, кликать в пустое место не нужно. «В архив» показывается
  только у сохранённой задачи и перед архивированием сохраняет текущие правки; у новой задачи
  кнопки нет, поэтому она не может «потеряться».
  Код: `TaskDetailModal.jsx`, `DateTimeField.jsx`, `App.handleDeleteTask`.
- [x] **Фокус в поле чата после Enter.** Поле ввода блокировалось на время отправки (`disabled={sending}`),
  из-за чего браузер снимал фокус с textarea. Теперь поле активно во время отправки, а `handleSend`
  дополнительно возвращает фокус через `composerRef`. Можно сразу печатать следующее сообщение.
- [x] **Показать пароль не работает на телефоне.** Кнопка-глаз была вложена в `<label>` — на мобильных
  тап уходил в поле пароля, а зона нажатия 15×15 px плохо ловила касание. Кнопка вынесена из `<label>`,
  зона 36×36 px, `onPointerDown` с `preventDefault`, добавлены `aria-label` и `aria-pressed`.
  Код: `LoginPage.jsx`.
- [x] **Архив удалённых задач.** Заложен в ФТ, но фактически не работал: архив грузился без прав доступа, без автора, без нумерации. Переписано: модалка архива, фильтрация по правам, подпись постановщика, восстановление, «удалить навсегда».
- [x] **Не переносятся задачи между блоками.** Причина: на доске `SortableContext` содержал *колонки*, а `Column` использовал `useSortable` — при перетаскивании карточки колонки начинали «сортироваться», перехватывая цель. Пустая область колонки не была droppable-зоной, а `over.id` карточки из другой колонки не находился. Исправлено: колонка — `useDroppable` с `data.type='Column'`, кастомная collision detection (pointerWithin → задача, иначе колонка), пересчёт `position` для обеих колонок.
- [x] **Нет списка просмотра команды.** Добавлен блок «Команда» (кнопка в шапке) со списком сотрудников, ролями и переходом в профиль каждого.
- [x] **Данные профиля в модалке не сохраняются.** Причина 1: `ProfileModal` возвращал `null`, если `profile === null` — модалка физически не открывалась (совпадает с прод-багом из handoff). Причина 2: `update` без существующей строки `profiles` молча ничего не делал. Исправлено: модалка открывается всегда (поля из `session.user`), сохранение через `upsert`, явные ошибки, `refreshProfile` после записи.
- [x] **Локальный адрес в базе / конфиге.** `supabaseClient.js` берёт URL/ключ из `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` с fallback на текущий проект; `redirectTo` строится от `window.location.origin` (не localhost). В Supabase нужно обновить Site URL и Redirect URLs — см. §4.
- [x] **Удалённые задачи команды — по правам доступа.** Правило: архив показывает личные удалённые задачи, только если `created_by = я`; командные — всем, кто видит задачу в активном состоянии (RLS + дублирующая проверка на клиенте), с подписью постановщика.
- [x] **Вход через Яндекс не работает «молча».** Проверено внешними запросами: провайдер `custom:yandex` настроен, Supabase отдаёт корректный 302 на `oauth.yandex.ru` с `redirect_uri=https://…supabase.co/auth/v1/callback`, Яндекс показывает форму входа (callback принят). Значит ломается возврат. Теперь ошибки из URL (`?error_code=…&error_description=…`) разбираются и показываются, есть панель «Диагностика Яндекс-входа» с точным Redirect URI, требованиями к Site URL и готовым SQL для auth-триггера. Причина класса «Database error saving new user» закрывается новым `handle_new_user()` в миграции.
- [x] **Доступ и регистрация.** Закрытая регистрация по приглашениям: таблица `invites`, guard-триггер на `auth.users`, поле «код приглашения» на форме, RPC-проверка кода. См. §4.
- [x] **Дата создания vs срок.** В карточке и модалке выводится **срок** (`due_at`), а не дата создания. Дата создания — только справочно в архиве.
- [x] **Дата должна содержать время, а не только число.** Срок — `datetime-local`, отображение «11 ноя, 14:30»; просроченные — красным.
- [x] **Нумерация задач с датой.** У задачи стабильный номер `№ 14` (из `task_no` или вычисленный по `created_at`), в карточке — `№ 14 · 11 ноя, 14:30`, в архиве — `№ 14 · создана 11 ноя 2026`.

### Фичи

- [x] **Личная задача — человечек.** Замок заменён на иконку человека в цветном бейдже + подпись «Личная»; личные задачи видны только автору.
- [x] **Выделение команды в отдельный блок.** Кнопка «Команда» → список (аватары, роли, контакты, Telegram) → клик по сотруднику открывает его профиль.
- [x] **Telegram в профиле сотрудника.** Поле `telegram` (`@nick` или `t.me/...`) с нормализацией, предпросмотром ссылки и кнопкой «Открыть»; в карточке сотрудника — кнопка «Написать в Telegram» + копирование ника. Ссылка `https://t.me/nick` открывает чат (приложение или веб). До миграции ник хранится локально (см. §8).
- [x] **Роли и права (шаг 4 из handoff).** Панель «Доступ» (кнопка в шапке): список сотрудников с выдачей ролей, приглашения (создание/отзыв, статус «ожидает/использовано»), матрица прав «роль × право». Роли: `admin/manager/deputy/member`. Международная логика прав — `lib/permissions.js` (`can()`), сервер — `is_admin()`, политика `profiles_update_admin`, триггер `protect_profile_role`, политики `invites_*` (миграция 003).
- [x] **Матрица прав.** 12 прав: задачи (создание/редактирование/архив/исполнители/приоритет/управление чужими), команда, роли, приглашения, колонки. Матрица доступна всем (просмотр), управление — по правам роли.
- [x] **Первый администратор в панели «Доступ».** Если роль не позволяет менять роли, селекты заблокированы, а сверху показывается понятный баннер без кода: «Роли меняет администратор, попросите администратора команды». Инструкция с SQL спрятана под ссылкой «Я владелец проекта — как назначить администратора?» (там код и кнопка «Копировать»). Свою роль через интерфейс изменить нельзя (только другим сотрудникам).
- [x] **Читаемые выпадающие списки.** Для `select.glass-input` заданы `color-scheme` (light/dark) и явные цвета `option` — в тёмной теме список ролей тёмный с белым текстом, в светлой — белый с тёмным. Не зависит от системной темы браузера.
- [x] **Логотип в шапке.** Прозрачный знак (`public/logo-mark.png`, белая подложка убрана из PNG), в тёмной теме подсвечивается фильтром. Клик по логотипу/названию всегда возвращает на главную: доска, сброс фильтров и выделения, закрытие всех модалок, скролл вверх.
- [x] **Перетягивание задач по рейтингу.** Задачи в колонке сортируются вручную (drag = рейтинг/порядок), `position` пересчитывается для всей колонки. Приоритет (Высокий/Средний/Низкий) — цветной индикатор.
- [x] **Календарь: читаемые подписи.** События окрашены по приоритету (высокий — красный, средний — оранжевый, низкий — зелёный, без приоритета — индиго), текст белый на цветной плашке; `eventDisplay="block"`, чтобы не превращались в точки; длинные названия обрезаются многоточием с полным текстом в подсказке. Цвета задаются и через CSS-переменные, и inline в `eventDidMount` — не зависят от темы.
- [x] **Диаграмма Ганта как в MS Project + выгрузка в файл.** Третий вид «Гант»: таблица задач (№, задача, исполнитель, начало, срок, дней) + таймлайн с месяцами, неделями и днями, подсветкой выходных и линией «сегодня»; масштабы Дни/Недели/Месяцы; полоса тянется (сдвиг сроков), правый край — длительность; сохранение в БД. Экспорт: **MS Project XML (MSPDI)**, **CSV/Excel**, **PDF через печать**. Код: `components/GanttView.jsx`, `lib/gantt.js`, `lib/export.js`.
- [x] **Массовое выделение задач (итерация 3).** Режим «Выделить»: чекбоксы на карточках, выделение колонки целиком, «Все», Esc — выход. Панель действий: перенос в колонку, назначение исполнителя, приоритет, «в архив». DnD в режиме выделения отключён — та самая причина, из-за которой фичу раньше откатили. Код: `components/BulkActions.jsx`.
- [x] **Внутренний чат: общий и личные (итерация 3).** Кнопка «Чат» в шапке с бейджем непрочитанных. Слева две группы: «Общий чат команды» (создаётся автоматически, видят все, у сообщений подпись автора) и «Личные» диалоги. Новый диалог — по кнопке «+» или «Начать диалог»: открывается отдельное окно «Кому написать» с поиском, список — только зарегистрированные активные пользователи (RPC `chat_candidates`). У каждого сообщения подписан автор: в общем чате «Вы» у своих и имя у остальных, в личном — имя собеседника. В списке сразу видны все зарегистрированные сотрудники без переписки — клик открывает личный диалог. Написать сотруднику можно и из «Команды»: маленькая иконка чата на карточке, а также кнопка «Написать в чат» (в подвале и иконка в шапке профиля). Переписка с группировкой по дням, отправка по Enter (Shift+Enter — перенос строки), Realtime, отметка прочитанного, Telegram-ссылка и переход в профиль из шапки диалога. Код: `ChatModal.jsx` + `ChatView.jsx` + `lib/chat.js`; схема — миграции 004 (диалоги/сообщения), 005 (общий чат), 006 (список собеседников), 007 (все сотрудники сразу участники общего чата).
- [x] **Календарь: день и неделя по часам + создание на время.** Вкладки «Месяц / Неделя / День»; в неделе и дне
  слева ось времени (06:00–23:00), линия «сейчас», пересекающиеся задачи рисуются блоками по `start_at`–`due_at`.
  Выделение слота мышью открывает новую задачу с уже заполненными началом и сроком — так ставятся встречи.
  Код: `CalendarView.jsx` (timeGrid), `handleCalendarSlot` в `App`; зависимость `@fullcalendar/timegrid`.
- [x] **Календарь: перетаскивание задач и многодневные задачи.** Событие можно перетащить на другой день
  или время: `eventDrop` сдвигает `start_at` и `due_at` на дельту (для all-day — календарные дни,
  для времени — миллисекунды), сохраняет в БД и обновляет состояние; при ошибке — `revert`.
  Задача, начатая сегодня и завершающаяся завтра/через несколько дней, рисуется all-day-полосой
  с `start = день начала`, `end = день срока + 1` (FullCalendar считает конец исключающим), поэтому
  видна **на каждом дне** и в месяце, и в неделе, и в дне. Внутри одного дня сохраняется timeGrid.
  Код: `CalendarView.jsx` (`events`, `handleEventDrop`), `App.handleCalendarTaskDateChange`.
  Заголовок периода капитализируется (`Ноябрь 2026 г.`), даже если FullCalendar отдаёт месяц
  со строчной буквы.
- [x] **Фильтр «Просрочено».** Чип «Просрочено: N» в строке статистики теперь кнопка: показывает
  только активные задачи с истёкшим сроком (задачи в «Готово» не считаются), работает вместе
  с режимами «Все / Команда / Личное» и фильтром по сотруднику. Повторный клик, крестик в шапке,
  смена режима или возврат на главную сбрасывают фильтр. Счётчик остаётся общим по текущей
  выборке, а «Задач» показывает `N из M`, когда фильтр включён.
  Код: `App.jsx` (`overdueOnly`, `scopedTasks`, `overdueTasks`), `lib/format.js` (`isTaskOverdue`),
  `Header.jsx` (чип активного фильтра).
- [x] **Аналитика для руководителей.** В «Команде» появилась вкладка **«Аналитика»** (видна
  администратору, менеджеру и заместителю): KPI «Всего / Выполнено / В работе / Просрочено / В срок»,
  структура задач, доля выполненных в срок, распределение по приоритетам и таблица по сотрудникам
  (всего, в работе, выполнено, просрочено, % в срок). Фильтр — отдельное окно: период (7/30/90 дней,
  год или свои даты) и сотрудник. Период считается по сроку задачи; архивные завершённые задачи
  учитываются, личные задачи и удалённые без завершения — нет. «Выполнено в срок» — по `done_at`
  относительно `due_at`; задачи без даты завершения в процент не входят.
  Код: `AnalyticsPanel.jsx`, `AnalyticsFiltersModal.jsx`, `lib/analytics.js`, вкладка в `TeamModal`.
- [x] **Повторяющиеся задачи.** В карточке появился блок **«Повторение»**: ежедневно / еженедельно /
  ежемесячно, опционально «повторять до» даты. Следующая дата показывается сразу. При завершении
  текущей задачи БД создаёт следующую копию в первой рабочей колонке: те же название, описание,

## 3. Правила разработки

1. Только функциональные компоненты + хуки, без классов.
2. Tailwind v4: `@import "tailwindcss"` + `@custom-variant dark`. Кастомные утилиты — в `index.css` (`glass`, `glass-panel`, `glass-input`, `glass-btn`, `app-bg`).
3. Не плодить зависимости: всё уже установлено.
4. Схема БД может отставать от кода → любое новое поле пишется только если оно есть в выборке (`lib/schema.js`), иначе запрос падает.
5. Ошибки Supabase всегда показываются пользователю, не только в консоль.
6. `key` для `TaskDetailModal` — по `id` задачи (иначе TipTap не пересоздаётся).
7. StrictMode не включать (двойные запросы).
8. Все пользовательские строки — на русском.
9. **Звуковое уведомление.** В конце каждого ответа (когда работа завершена и нужна проверка заказчика)
   запускать `tools/notify-done.cmd` — мягкие колокольчики `C:\Windows\Media\chimes.wav` (~1,6 с).
   Если заказчик просит другой звук — поменять файл в `.cmd` (`ding.wav`, `Windows Notify System Generic.wav`,
   `Alarm*.wav`). Скрипт `.ps1` в системе может блокироваться политикой выполнения — использовать `.cmd`.

## 8. Известные ограничения / следующий шаг

1. **Приватность личных контактов** сейчас маскируется только в UI (`show_personal_data`).
   Через PostgREST строка профиля отдаётся целиком. Полная защита — отдельное
   представление `team_directory` с `null` для чужих личных полей и запрет прямого select.
2. **Код приглашения** — второй фактор, проверяется в RPC и в guard-триггере только по email.
   Полная проверка кода на сервере — через Auth Hook (before user created).
3. **Файлы** в бакете `task-files` публичные (Public URL). Для приватности — signed URL и RLS на Storage.
4. **Realtime** подключён только в чате (`messages`). Доска, задачи и профили не подписаны —
   их изменения видны после перезагрузки.
5. **История/аудит** удалений (`deleted_by`) фиксируется, но отдельной ленты событий нет.
6. **Гант:** нет зависимостей между задачами (стрелок-предшественников), вех и базового плана —
   следующий шаг, если нужно «совсем как MS Project». Перетаскивание сроков доступно
   только после миграции (`start_at` + `due_at`), иначе диаграмма работает в режиме просмотра.
7. **Telegram до миграции** живёт в `localStorage` браузера: владелец видит свой ник, но команда
   — только после применения `002_telegram.sql` (или `001`). В форме профиля об этом есть
   предупреждение и кнопка «SQL» для копирования нужного запроса.
8. **Массовые действия** пишут только те поля, что есть в схеме: перенос колонки и архив работают
   всегда, «исполнитель» и «приоритет» появятся после миграции (сейчас кнопки скрыты через `supports`).
9. **Bucket `avatars` публичный** (как и `task-files`): картинку по прямой ссылке может открыть любой,
   кто её знает. Для приватности — signed URL и приватный bucket.
10. **Файлы чата лежат в публичном bucket `chat-files`** с неугадываемым UUID в пути: сообщение видят
    только участники диалога, но сама ссылка на файл не проверяет доступ. Для строгой приватности —
    signed URL и политика чтения по `is_conversation_member`.
11. **Runtime-прокси на Layero Free:** холодный старт 4–12 с после простоя (первый вход может
    подтормозить), лимиты 6 000 минут/мес и 300 тыс. запросов. Если станет тесно — тот же `server.js`
    переезжает на VPS за 300–600 ₽/мес без изменений кода.
12. **Вход через Яндекс — пауза (13.11.2026).** Сделано: включён `manual linking`, в `custom:yandex`
    прописан `attribute_mapping` (`sub←id`, `email←default_email`, `email_verified: true`, `name←real_name`),
    обмен токена и userinfo идут через `kanban.layero.app/yandex-token` и `/yandex-userinfo`
    (Яндекс требует `Authorization: OAuth`, Supabase шлёт `Bearer`; прокси меняет схему и приводит `id`
    к строке). Яндекс отвечает 200 и на токен, и на профиль. Но привязка всё ещё падает с 500
    на шаге создания identity; последняя попытка была **до** деплоя нормализации `id`.
    Следующий шаг: одна попытка на свежей сборке, затем проверить `/yandex-last` (`idType`),
    `/client-oauth-last` и `auth.identities`; если 500 остаётся — смотреть Auth Logs в Supabase
    (Management API `analytics/endpoints/logs` у проекта отвечает `Backend error`).
    Вход по почте и паролю при этом работает штатно.
    **UI временно скрыт** флагом `YANDEX_LOGIN_ENABLED = false` в `src/lib/features.js`
    (кнопка на входе и блок привязки в профиле). Вернуть — поставить `true`.
    Скриншот входа без Яндекса: `login-no-yandex.png`.
